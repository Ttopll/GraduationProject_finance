# 基于规则引擎的家庭财务管理系统的设计与实现

## 摘要

随着移动支付、银行卡、网络消费和家庭多成员共同支出的普及，个人及家庭日常财务数据呈现出来源分散、类型复杂、记录不连续等特点。传统手工记账方式依赖用户主动维护，容易出现漏记、分类不统一、预算执行情况难以及时掌握等问题。针对上述情况，本文设计并实现了一套基于规则引擎的家庭财务管理系统。系统以家庭为基本管理单位，围绕用户认证、家庭成员管理、账户管理、收支分类、交易流水、预算管理、规则预警、通知提醒和真实数据分析等功能展开，实现了从数据录入、分类维护、预算监控到规则触发提醒的业务闭环。

系统后端采用 Spring Boot、Spring Data JPA、Spring Security、MySQL 等技术实现，使用 JWT 完成登录认证，通过家庭成员关系控制数据访问范围。管理员端采用 Vue3 实现，用于维护基础业务数据、查看真实数据分析结果和管理规则通知；小程序端面向普通用户，提供家庭首页、账户、交易、预算、通知和个人中心等功能。系统规则引擎支持基于家庭支出、分类支出、预算使用率等指标进行阈值判断，并在规则命中后生成站内通知。为增强系统的数据分析支撑，项目还引入 Online Retail、World Bank 和 FRED 等真实数据来源，完成数据清洗、入库和分析接口展示。

测试结果表明，系统能够完成用户登录、家庭上下文建立、业务数据维护、预算使用率计算、规则评估、通知生成以及真实数据分析等核心流程，基本满足家庭财务管理系统的设计目标。

关键词：家庭财务管理；规则引擎；预算预警；Spring Boot；微信小程序；Vue3

## Abstract

With the popularity of mobile payment, bank cards, online consumption and multi-member household spending, family financial data has become increasingly scattered and difficult to manage manually. Traditional bookkeeping methods rely heavily on users' manual input and are prone to missing records, inconsistent categories and delayed budget feedback. To address these problems, this thesis designs and implements a household financial management system based on a rule engine. The system uses family as the basic management unit and provides functions such as user authentication, family member management, account management, category management, transaction records, budget management, rule-based alerts, notifications and real-data analysis.

The backend is implemented with Spring Boot, Spring Data JPA, Spring Security and MySQL. JWT is used for authentication, and family membership is used to control data access. The administrator web application is implemented with Vue3, supporting business data management, real-data analysis and rule notification management. The mini program is designed for household users and provides pages for home overview, accounts, transactions, budgets, notifications and profile. The rule engine supports threshold evaluation based on family expenses, category expenses and budget usage. When rules are triggered, notifications are generated automatically. In addition, real datasets from Online Retail, World Bank and FRED are introduced to support data import and analysis.

The test results show that the system can complete key workflows including login, family context creation, business data maintenance, budget usage calculation, rule evaluation, notification generation and real-data analysis, which basically meets the design objectives of the household financial management system.

Keywords: household financial management; rule engine; budget alert; Spring Boot; WeChat mini program; Vue3

## 第 1 章 绪论

### 1.1 研究背景

家庭财务管理是个人信息化管理中的重要内容。随着消费场景不断增多，家庭成员可能同时使用现金、银行卡、微信、支付宝、信用卡等多种账户进行支付，财务数据来源变得更加分散。对于普通家庭而言，收入、日常支出、预算、债务、资产等数据如果长期缺少统一记录，就难以及时判断家庭财务状况，也不利于后续进行预算控制和消费结构分析。

目前常见的记账软件通常能够完成基本收支记录，但在家庭协同、预算预警、规则化提醒和多端联通方面仍存在不足。部分系统只提供简单账本功能，用户需要主动查看预算是否超支；部分系统虽然支持图表展示，但缺少可以根据实际业务规则自动触发提醒的机制。基于此，本文将规则引擎引入家庭财务管理场景，使系统不仅能够记录数据，还能够根据规则主动发现风险并生成通知。

### 1.2 研究意义

本课题的意义主要体现在三个方面。第一，在业务层面，系统将家庭成员、账户、分类、预算、交易和通知整合到同一平台中，能够帮助用户形成相对完整的家庭财务数据闭环。第二，在技术层面，系统通过规则定义、规则评估和通知生成实现轻量级规则引擎，将固定业务判断从普通代码逻辑中抽离出来，提高了系统扩展能力。第三，在展示与分析层面，系统引入真实数据导入和分析功能，使项目不仅停留在模拟数据录入，还能够结合外部真实数据进行趋势和结构分析。

### 1.3 国内外研究现状

当前家庭财务管理类系统主要包括个人记账工具、银行类账单管理工具以及综合理财平台。个人记账工具通常操作简单，适合记录日常收入和支出，但对家庭成员协同和规则预警支持不足。银行或支付平台提供的账单系统数据来源较准确，但往往局限于单个平台，难以统一管理其他渠道数据。综合理财平台具备资产分析和投资建议功能，但系统复杂度较高，普通家庭使用时存在学习成本。

从技术实现角度看，规则引擎常被应用于风控、审批、推荐和监控告警等场景。其核心思想是将判断条件和执行动作配置化，使系统能够在业务规则变化时减少硬编码改动。本文结合毕业设计规模，没有采用复杂商业规则引擎，而是实现了轻量级规则定义与评估机制，用于支持家庭支出阈值、分类预算超支、连续高支出和趋势异常等判断。

### 1.4 本文主要工作

本文主要完成以下工作：

1. 设计并实现家庭财务管理系统的后端服务，包括用户认证、家庭管理、账户、分类、预算、交易、通知、债务、资产和真实数据分析等模块。
2. 设计系统数据库结构，围绕用户、家庭、成员、账户、分类、交易、预算、规则、通知和外部数据建立实体关系。
3. 实现轻量级规则引擎，支持规则定义、启停、手动评估、执行日志和通知生成。
4. 实现管理员端 Vue3 页面，用于系统管理、业务数据维护、规则通知管理和真实数据分析展示。
5. 实现微信小程序端 MVP，用于普通用户查看家庭首页、账户、交易、预算、通知和个人信息。
6. 引入真实数据文件，完成数据清洗、导入数据库和分析接口对接。

本文共分为六章。第一章介绍研究背景、意义和主要工作。第二章分析系统需求。第三章介绍系统总体设计，包括技术架构、功能模块和数据库设计。第四章说明核心功能实现。第五章进行系统测试与结果分析。第六章总结全文并提出后续改进方向。

## 第 2 章 系统需求分析

### 2.1 可行性分析

从技术可行性看，系统采用 Spring Boot 和 MySQL 作为后端主要技术，具有成熟的生态和较好的开发效率。管理员端使用 Vue3，小程序端使用微信小程序原生开发方式，均能够满足本课题的展示和交互需求。从经济可行性看，系统开发依赖的主要软件和框架均可免费使用，部署和测试可在本地完成，成本较低。从操作可行性看，系统按照家庭财务管理的常见流程设计，用户可以通过登录、选择家庭、维护账户分类、录入交易、查看预算和通知完成主要操作。

### 2.2 用户角色分析

系统主要包括管理员端用户和小程序端用户。管理员端用户主要负责系统数据维护、业务数据管理、真实数据分析和规则通知配置。小程序端用户主要面向家庭成员，负责查看家庭财务概览、维护账户与交易、查看预算执行情况和接收通知提醒。

系统以家庭为数据隔离单位。用户登录后需要关联到一个家庭，后续账户、分类、预算、交易、规则和通知等数据均绑定家庭 ID，从而避免不同家庭之间的数据混用。

### 2.3 功能需求

系统功能需求主要包括以下部分。

用户认证模块需要支持用户注册、登录和当前用户信息获取。用户登录成功后，系统返回 JWT，后续请求通过请求头携带 Token 完成身份认证。

家庭管理模块需要支持创建家庭、通过邀请码加入家庭、查询家庭成员和维护家庭上下文。系统中的业务数据均依赖家庭上下文。

账户与分类模块需要支持维护家庭账户和收支分类。账户用于记录现金、银行卡、支付账户等资金来源，分类用于对收入和支出进行归类。

交易流水模块需要支持录入收入、支出和转账数据，并在录入交易后更新账户余额。交易数据是预算统计、财务分析和规则评估的基础。

预算模块需要支持创建预算、查询预算列表和计算预算使用情况。当预算达到预警比例或超支时，系统可以联动规则与通知模块。

规则引擎模块需要支持规则定义、规则启停、规则评估和通知生成。规则条件包括家庭总支出、分类支出、阈值比较、连续超阈和趋势异常等。

通知模块需要支持查询通知、标记已读、批量已读和删除已读通知。通知来源包括预算提醒、规则触发和债务提醒等。

真实数据分析模块需要支持导入外部真实数据，并提供零售交易概览、国家消费趋势和宏观经济序列查询接口。

### 2.4 非功能需求

系统应具备基本安全性，受保护接口必须在用户登录后访问。系统应具备一定可维护性，后端按照 controller、service、repository、entity、dto 等层次组织代码。系统应具备可扩展性，规则定义和通知生成应尽量避免写死在单个业务流程中。系统还应具备可演示性，管理员端和小程序端能够展示主要业务流程，便于毕业设计答辩和系统验收。

## 第 3 章 系统总体设计

### 3.1 系统架构设计

系统采用前后端分离架构。后端提供统一 REST API，负责业务逻辑、权限校验、数据持久化和规则评估。管理员端通过 Vue3 调用后端接口，提供后台管理界面。小程序端通过微信开发者工具运行，面向普通用户提供移动端交互。

后端主要技术包括 Spring Boot、Spring Data JPA、Spring Security、MySQL、JWT 和 OpenCSV。Spring Boot 用于快速构建 Web 服务，Spring Data JPA 用于简化数据库访问，Spring Security 和 JWT 用于认证鉴权，MySQL 用于保存业务数据，OpenCSV 用于账单和真实数据文件处理。

### 3.2 后端分层设计

后端代码主要分为以下层次：

controller 层负责接收 HTTP 请求并返回响应结果，例如 `AuthController`、`FamilyController`、`TransactionRecordController`、`RuleDefinitionController` 和 `RealDataAnalysisController`。

service 层负责业务逻辑处理，例如 `AuthService`、`FamilyService`、`BudgetService`、`TransactionRecordService`、`RuleEvaluationService` 和 `RealDataAnalysisService`。

repository 层负责数据库访问，通过 Spring Data JPA 对实体进行增删改查。

entity 层对应数据库表结构，例如 `SysUser`、`Family`、`FamilyMember`、`Account`、`Category`、`TransactionRecord`、`BudgetPlan`、`RuleDefinition`、`Notification` 等。

dto 层用于定义接口请求和响应模型，减少实体类直接暴露给前端。

security 层负责登录用户解析、JWT 校验和家庭访问权限控制。

### 3.3 功能模块设计

系统按照业务功能划分为认证与用户、家庭成员、账户分类、交易流水、预算管理、规则引擎、通知中心、真实数据分析、管理员端和小程序端等模块。

认证与用户模块负责登录注册和用户上下文建立。家庭成员模块负责维护家庭组织关系。账户分类模块负责维护财务基础资料。交易流水模块记录具体收支行为。预算模块根据交易数据计算预算使用率。规则引擎模块根据配置规则判断是否触发提醒。通知中心模块负责保存和展示提醒结果。真实数据分析模块用于导入和分析外部真实数据。

### 3.4 数据库设计

数据库以家庭财务数据为核心，主要包括用户表、家庭表、家庭成员表、账户表、分类表、交易流水表、预算表、规则定义表、规则执行日志表、通知表、债务表、资产表和外部真实数据表。

用户表保存系统用户的基本信息和登录凭证。家庭表保存家庭名称、邀请码、币种和时区等信息。家庭成员表建立用户与家庭之间的关系，并记录成员角色。账户表保存家庭资金账户信息。分类表保存收入和支出分类。交易流水表保存每一笔收入、支出或转账记录。预算表保存预算金额、周期、预警比例和有效期。规则定义表保存规则类型、指标类型、比较符、阈值和通知模板。规则执行日志表记录每次评估结果。通知表保存规则或预算触发后的站内消息。

真实数据分析部分包括外部零售交易表、World Bank 家庭消费数据表和 FRED 宏观序列表，用于保存清洗后的外部数据。

### 3.5 权限与数据隔离设计

系统使用 JWT 保存登录状态。用户登录后，后端根据 Token 解析当前用户身份。涉及家庭数据的接口需要校验用户是否属于对应家庭。这样可以避免用户访问其他家庭的数据。管理员端和小程序端在使用业务接口前，都需要先完成登录并获得当前家庭上下文。

## 第 4 章 系统核心功能实现

### 4.1 用户认证与家庭上下文实现

用户通过登录接口提交用户名和密码，后端校验成功后生成 JWT 并返回给前端。前端保存 Token，后续请求在 Authorization 请求头中携带。后端过滤器解析 Token 后构建当前登录用户上下文。

家庭上下文是系统业务运行的基础。创建家庭时，系统会将创建者写入家庭成员表并赋予家庭所有者角色。用户加入家庭后，也会形成家庭成员记录。账户、分类、预算、交易、规则和通知等数据均绑定家庭 ID。

### 4.2 账户、分类与交易流水实现

账户模块用于维护现金、银行卡、支付账户等家庭资金账户。分类模块用于维护收入和支出分类。交易流水模块支持收入、支出和转账。创建支出交易时，系统会减少对应账户余额；创建收入交易时，系统会增加账户余额；转账交易则涉及来源账户和目标账户之间的余额变化。

交易流水不仅用于记录日常收支，也是预算统计、规则评估和财务分析的基础数据。因此在系统实现中，交易记录与账户、分类、家庭成员之间建立了明确关联。

### 4.3 预算管理与预算使用率计算

预算模块允许用户为某个分类设置月度预算金额和预警比例。系统根据预算周期查询对应时间范围内的交易支出，并计算预算使用率。当使用率达到预警比例或超过预算金额时，该预算会被识别为风险预算。

预算使用情况可以在管理员端和小程序端展示，也可以作为规则引擎的输入条件。通过这种方式，预算模块不只是静态配置，而是能够和交易、规则、通知形成联动。

### 4.4 规则引擎实现

系统实现了轻量级规则引擎，核心数据表为规则定义表。规则定义包括规则名称、规则类型、指标类型、时间范围、比较符、阈值、关联分类、动作类型、通知模板和优先级等字段。

规则评估服务会读取当前家庭启用的规则，根据规则类型计算对应指标。例如，分类支出规则会统计指定分类在指定月份内的支出金额，然后与阈值进行比较。若规则命中，系统会写入规则执行日志，并调用通知服务生成通知。

目前系统支持单点阈值、连续超阈和趋势异常等规则类型。单点阈值适合判断本月支出是否超过固定金额；连续超阈适合判断连续多个月支出是否偏高；趋势异常适合判断本月数据相对历史均值是否增长明显。

### 4.5 通知中心实现

通知模块用于保存系统生成的提醒信息。通知来源包括规则触发、预算预警和债务提醒。通知数据包括标题、内容、等级、来源类型、读取状态和创建时间等信息。

管理员端可以查看通知列表、筛选未读通知、批量设为已读和删除已读通知。小程序端可以查看通知中心，并将提醒作为用户日常查看预算风险的重要入口。

### 4.6 真实数据导入与分析实现

为提升项目的数据支撑能力，系统引入了真实数据采集和导入流程。当前项目包含 Online Retail 交易数据、World Bank 家庭消费数据和 FRED 宏观经济序列数据。数据经过脚本抓取和清洗后存放在 `data/processed` 目录下。

后端通过真实数据分析接口导入清洗后的 CSV 文件，并写入外部数据表。导入后，系统提供零售交易概览、国家消费趋势、宏观序列查询和答辩摘要接口。管理员端真实数据分析页面可以调用这些接口，展示真实数据导入结果和分析结论。

### 4.7 管理员端实现

管理员端基于 Vue3 实现，采用标准后台页面结构。主要页面包括登录页、总控台、真实数据分析、用户与家庭、业务数据管理、资产与负债、导入导出、账单解析规则、规则与通知和系统说明等。管理员端用于集中展示系统功能，完成基础数据维护、规则配置和分析结果查看。

其中规则与通知页面用于展示规则引擎闭环，包括风险预算、规则覆盖、规则列表和通知列表。真实数据分析页面用于展示外部数据导入、零售概览、国家趋势和宏观数据结果。

### 4.8 小程序端实现

小程序端面向普通家庭用户，提供登录、首页、账户、交易、预算、通知、个人中心和家庭信息等页面。用户可以在小程序中查看家庭财务基础信息，新增或查看账户、交易和预算，接收系统通知。小程序端与管理员端共用后端接口，从而形成两端联通。

## 第 5 章 系统测试与结果分析

### 5.1 测试环境

系统测试环境主要包括 Windows 操作系统、JDK 17、Maven、MySQL 8、Node.js、微信开发者工具和浏览器。后端服务默认运行在 `http://localhost:8088`，管理员端通过 Vite 本地开发服务运行，小程序端通过微信开发者工具运行。

### 5.2 后端接口测试

后端接口测试主要围绕用户登录、家庭创建、账户分类维护、交易录入、预算查询、规则评估、通知查询和真实数据分析进行。测试过程中，首先注册并登录用户，获取 Token；随后创建家庭并维护账户、分类、预算和交易；最后执行规则评估并查询通知结果。

测试结果表明，系统能够完成基本接口调用，家庭上下文能够正常传递，交易数据能够影响账户余额和预算统计，规则评估后能够生成通知。

### 5.3 管理员端测试

管理员端测试主要检查页面是否能正常加载、登录是否成功、业务数据表格是否能查询、新增和编辑是否能提交、真实数据分析是否能展示、规则与通知页面是否能完成规则维护和通知查看。

项目中新增了 Vue 单文件解析检查脚本，用于快速判断管理员端页面是否存在模板语法错误。当前 18 个 Vue 文件均能通过解析检查。

### 5.4 小程序端测试

小程序端测试主要通过微信开发者工具完成。测试内容包括登录、进入家庭首页、查看账户总览、新增账户、新增交易、查看预算、进入通知中心和查看个人信息等。测试结果表明，小程序端能够调用本地后端接口，并与管理员端共享家庭业务数据。

### 5.5 真实数据分析测试

真实数据分析测试主要验证 CSV 文件是否存在、导入接口是否能够入库、零售交易概览接口是否返回交易总数和金额、World Bank 趋势接口是否返回国家消费趋势数据、FRED 接口是否能够处理宏观序列数据。由于 FRED 数据获取受网络影响，系统允许其软降级为空文件或仅表头，但不影响主要真实数据分析流程。

### 5.6 测试结论

综合测试结果看，系统已经能够完成毕业设计所需的主要功能闭环，包括用户认证、家庭数据隔离、业务数据维护、预算统计、规则评估、通知提醒、真实数据分析以及两端页面展示。但系统仍存在一些不足，例如测试覆盖率不够高、前端页面细节仍需优化、规则引擎还不支持复杂组合条件、外部消息推送尚未接入等。

## 第 6 章 总结与展望

### 6.1 工作总结

本文设计并实现了一套基于规则引擎的家庭财务管理系统。系统围绕家庭财务管理的实际需求，完成了用户认证、家庭成员、账户分类、交易流水、预算管理、规则预警、通知中心、真实数据分析、管理员端和小程序端等功能。后端采用 Spring Boot 分层架构，前端包括 Vue3 管理员端和微信小程序端，数据库采用 MySQL 保存业务数据。

系统的核心特色在于引入了规则引擎思想，将预算和交易数据与规则评估、通知提醒进行联动，使系统不仅能够记录家庭财务数据，还能够主动发现预算风险并提醒用户。此外，系统引入真实数据分析模块，为论文和答辩提供了更具体的数据支撑。

### 6.2 不足与改进方向

由于开发时间有限，系统仍有改进空间。首先，规则引擎仍属于轻量级实现，后续可以支持更复杂的组合条件、规则分组和规则优先级冲突处理。其次，通知模块目前主要是站内通知，后续可以接入微信订阅消息、短信或邮件推送。第三，前端页面虽然已经完成主要功能展示，但在交互细节和图表可视化方面仍可继续优化。第四，系统测试以功能验证为主，后续应增加更多单元测试、集成测试和异常场景测试。最后，真实数据分析还可以扩展更多指标，例如消费结构变化、国家间对比和宏观经济趋势预测等。

### 6.3 结论

总体来看，本文所设计的家庭财务管理系统已经实现了从数据录入、预算统计、规则评估到通知提醒的业务闭环，并完成了管理员端和小程序端的基本联通。系统能够较好地体现基于规则引擎的家庭财务管理思路，具有一定实用价值和扩展空间，基本达到了毕业设计的预期目标。
